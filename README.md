# When the Caption Lies

Do vision-language models believe a false claim over the chart in front of them, and does it matter **who** made the claim?

This repository holds the code for my COSC 4463 (AI, Language & Interaction) final project. It builds a small test set of synthetic financial charts, pairs each chart with a claim that contradicts it, and varies where that claim comes from:

| Condition | Where the false claim appears |
|---|---|
| `chart_only` | Nowhere. Baseline: can the model read the chart? |
| `caption` | A caption attached to the chart |
| `user_claim` | The user's turn, as a bare assertion |
| `user_opinion` | The user's turn, framed as an opinion ("I think ...") |
| `user_expert` | The user's turn, attributed to an expert ("According to a senior equity analyst ...") |
| `prior_assistant` | A scripted false statement placed in the model's own earlier turn |
| `self_caption` | The model first describes the chart itself (a real reply from a separate call), then the user asserts the claim as in `user_claim` |
| `self_caption_noclaim` | Control: the same self-description turn, then the question with no claim. Shows whether asking one turn after the image changes accuracy by itself |

The false claim is generated by a template, never written by hand. It states the opposite of the chart's true direction ("rose" for a falling chart) using the chart's own company, metric, and time span, and the sentence is word-for-word the same in every claim condition. Differences between conditions therefore come from the claim's source and framing, not its wording.

The verb pair can be changed with `--verbs` (`rose`/`fell` by default, or `increased`/`decreased`, or `went up`/`went down`) to check that results do not depend on one wording. Each wording is saved to its own results file.

The self-description is generated once per chart and model, then reused by every condition and wording that needs it, so those comparisons are paired on identical descriptions.

Comparing `user_claim`, `user_opinion`, and `user_expert` tests whether framing changes sycophantic acceptance. Comparing `self_caption` with `user_claim` (identical final turn) tests whether committing to its own reading makes a model more resistant.

## Quick start

```bash
pip install -r requirements.txt

# 1. Make the charts (200 by default, half rising and half falling)
python generate_charts.py --n 200

# 2. See exactly what a model is sent, without calling anything
python run_experiment.py --provider mock --dry-run --limit 1

# 3. Test the whole pipeline with a simulated model (no API key needed)
python run_experiment.py --provider mock --out results/mock/raw
python analyze.py --raw results/mock/raw --out results/mock
```

The mock model is fake. Its numbers are made up on purpose, so the tables and figures it produces are stamped "MOCK DATA." Use it only to check that everything runs.

## Running real models

Every provider uses the same command; only `--provider` and `--model` change. Runs can be stopped and restarted, and finished items are skipped.

| Provider | Cost | Setup | Example |
|---|---|---|---|
| Google Gemini | Free tier (rate-limited, roughly 100 requests per day on Flash models) | Get a key at aistudio.google.com, then `export GEMINI_API_KEY=...` | `python run_experiment.py --provider gemini --model gemini-2.5-flash --limit 25 --sleep 13` |
| Ollama (local, open-weight) | Free | Install Ollama, then `ollama pull qwen2.5vl:7b` | `python run_experiment.py --provider ollama --model qwen2.5vl:7b` |
| OpenRouter or another OpenAI-compatible API | Some free models; others a few cents | `export OPENROUTER_API_KEY=...` | `python run_experiment.py --provider openai --base-url https://openrouter.ai/api/v1 --key-env OPENROUTER_API_KEY --model <model-id>` |
| OpenAI | Paid | `export OPENAI_API_KEY=...` | `python run_experiment.py --provider openai --model gpt-4.1-mini` |
| Anthropic | Paid | `export ANTHROPIC_API_KEY=...` | `python run_experiment.py --provider anthropic --model claude-haiku-5-5` |

Model names change often. Check the provider's current model list and pass the id with `--model`. All calls use temperature 0.

Then score everything:

```bash
python analyze.py
```

### Control condition

`--polarity consistent` makes the claim agree with the chart instead. Comparing the two runs shows whether a model weighs the claim against the chart or just repeats whatever the text says.

## What gets measured

`analyze.py` writes `results/summary.csv`, `results/summary.md`, `results/stats.md`, and figures in `results/figures/`. `stats.md` holds the planned tests for H1 to H3 (exact McNemar tests, Holm-corrected within each model, with a count of the wordings that support each one), the cross-model comparisons (Qwen 3B versus 7B, Gemma versus Gemini, on charts both models read correctly), exploratory comparisons, and a split by the chart's true direction. The planned and cross-model tests are also saved as `results/planned_tests.csv` and `results/cross_model_tests.csv`.

- **Accuracy**: share of answers that match the chart, with 95% Wilson intervals.
- **Follow rate**: share of answers that match the false claim.
- **Flip rate**: among charts the model read correctly with no claim, the share it switched to the claim's direction. This is the main measure, because it leaves out charts the model could not read in the first place.
- **Conflict rate**: among correct answers, the share whose explanation points out the disagreement. This uses a keyword list, so hand-check a sample before reporting it.
- **Parse rate**: share of replies that could be read as "increase" or "decrease."
- **Own-description accuracy** (`self_caption` only): share of the model's own first-step descriptions that got the direction right.

Run a subset of conditions with `--conditions`, for example `--conditions chart_only user_claim user_opinion user_expert self_caption`. This is useful for rate-limited APIs.

## Hand annotation

`annotate.py` samples 120 replies to the six claim conditions (20 per condition, split across models, aiming for half correct and half incorrect) into a blind Excel sheet with the model and condition hidden:

```bash
python annotate.py sample   # annotation/annotation_sheet.xlsx and annotation/key.csv
python annotate.py recode   # a week later: 30 of the same replies, in a new order
python annotate.py score    # label shares per model, Cohen's kappa, keyword-detector check
```

Each reply gets one label: repair, adopt, hedge, silent, or self-contradiction. The sheet's Guide tab defines them and gives the order to use when more than one fits.

```

run_experiment.py       send charts x conditions to one model, save raw replies
analyze.py              parse replies, compute metrics, run the statistical tests, draw figures

caption_lies/
  charts.py             chart generation (invented companies, 3 metric types)
  conditions.py         the eight conditions and the exact prompt wording
  models.py             adapters for Gemini, OpenAI-compatible, Anthropic, Ollama, mock
  scoring.py            reply parsing, conflict heuristic, Wilson intervals
tests/                  run with: python -m pytest
data/                   generated charts (seed 4463)
results/                raw replies, summaries, and figures
```

## Design notes

- **Charts.** Each chart shows one invented company and one metric: monthly stock price (line), quarterly revenue (bar), or operating margin (line). The total change is 15% to 60%, and the series is re-drawn until both the endpoints and the fitted slope agree with the label, so the right answer is never a judgment call. Titles are neutral and never describe the trend.
- **Balance.** Exactly half the charts rise and half fall.
- **Reproducibility.** Everything is seeded (`--seed 4463`), and every raw reply is saved with a timestamp.
- **Harder charts.** `--noise hard` adds more noise to each series, for a difficulty analysis.
